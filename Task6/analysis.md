- **Где:** namespace `kube-system`, ресурс `secrets` (попытка `list`)

## Ошибки политики RBAC

1. **Отсутствие ограничений на создание высокопривилегированных RoleBinding.** Любой пользователь с правами `create rolebindings` смог привязать произвольный ServiceAccount к `cluster-admin`. Необходимо применить Gatekeeper/OPA-политику, запрещающую создание RoleBinding с `cluster-admin` без дополнительного подтверждения.

2. **Нет PodSecurity Admission.** Запрос на создание привилегированного контейнера прошёл без каких-либо предупреждений или блокировок. Необходимо настроить `PodSecurity` на уровне namespace (`enforce: restricted` или минимально `baseline`).

3. **Доступ к `pods/exec` в `kube-system` не ограничен.** Пользователь смог выполнить команду внутри системного пода CoreDNS без дополнительных проверок. Право `pods/exec` в системных namespace должно быть явно ограничено и требовать отдельной роли с аудитом каждого применения.

4. **Impersonation (`--as`) не требует дополнительной авторизации.** `minikube-user` использовал `--as=system:serviceaccount:secure-ops:monitoring` и `--as=admin` для разведки. Impersonation должна быть доступна только специальной привилегированной роли, а каждый факт использования — алертиться.

5. **Группа `system:masters` не имеет ограничений.** Все атакующие действия выполнялись под `minikube-user` с группой `system:masters`, которая обходит RBAC и имеет абсолютные права. В production этой группы быть не должно — нужны именованные роли с минимальными привилегиями.
