# Требования к внешним интеграциям: Умный дом
## PropDevelopment — Task 3

---

## 1. Описание интеграции

PropDevelopment интегрируется с внешней платформой партнёра для реализации двух сервисов умного дома:

| Сервис | Описание | Категория данных |
|---|---|---|
| Интеллектуальный домофон | Видеодомофон + автоматическое открытие по биометрии лица | **Биометрия — специальная категория ПД (152-ФЗ ст. 11)** |
| Интеллектуальный шлагбаум | Управление въездом + распознавание гос. номеров авто | Персональные данные (152-ФЗ) |

Сервисы доступны через мобильное приложение собственника (Витрина ЖКУ).

Новый компонент **smart-home-gateway** выступает единственной точкой интеграции PropDevelopment с платформой партнёра — tenant-core-app и мобильное приложение обращаются только к нему.

## 2. Требования к безопасности

### 2.1. Защита биометрических данных

Биометрические шаблоны распознавания лиц — специальная категория ПД по ст. 11 152-ФЗ. Для них устанавливается режим повышенной защиты.

| № | Требование |
|---|---|
| БИО-1 | Биометрические шаблоны **хранятся исключительно на платформе партнёра** и не передаются в системы PropDevelopment |
| БИО-2 | Серверы партнёра, хранящие биометрию, **физически расположены в РФ** (ст. 18.1 152-ФЗ) — закрепляется в DPA |
| БИО-3 | Регистрация биометрии возможна **только с явного письменного согласия** пользователя через мобильное приложение |
| БИО-4 | Согласие отзываемо: при отзыве биометрия удаляется у партнёра в течение **30 дней** |
| БИО-5 | PropDevelopment хранит только: `user_id` (UUID-псевдоним), статус согласия, дата регистрации/отзыва |
| БИО-6 | Срок хранения биометрии у партнёра — не более срока действия согласия, автоудаление по истечении |
| БИО-7 | Изоляция по `complex_id`: биометрия одного ЖК недоступна устройствам другого ЖК |

### 2.2. Защита данных о транспортных средствах

| № | Требование |
|---|---|
| ТС-1 | Гос. номер авто в связке с `user_id` является ПД — обрабатывается по 152-ФЗ |
| ТС-2 | В smart-home-db хранится **хэш номера** (SHA-256), а не номер в открытом виде |
| ТС-3 | Партнёру передаётся только хэш; маппинг `hash → реальный номер` хранится исключительно в smart-home-db |
| ТС-4 | Камеры шлагбаума не сохраняют видеозаписи всех проезжающих — только сверка с whitelist |
| ТС-5 | Срок хранения: до момента удаления собственником или прекращения права собственности |

### 2.3. Изоляция данных (мультитенантность)

| № | Требование |
|---|---|
| МТ-1 | Платформа партнёра обеспечивает **строгую изоляцию данных** между жилыми комплексами по `complex_id` |
| МТ-2 | Каждый API-запрос PropDevelopment содержит обязательный параметр `complex_id`; партнёр проверяет принадлежность |
| МТ-3 | Нарушение изоляции (доступ к данным другого ЖК) — критический инцидент, основание для расторжения договора |
| МТ-4 | Ежегодный пентест платформы партнёра с проверкой изоляции; отчёт предоставляется PropDevelopment |

### 2.4. Физическая безопасность и отказоустойчивость

| № | Требование |
|---|---|
| ФИЗ-1 | Устройства работают в **автономном режиме**: при потере связи с платформой используют локально кешированный whitelist |
| ФИЗ-2 | Максимальное время автономной работы: **72 часа**; по истечении — уведомление диспетчеру ЖК |
| ФИЗ-3 | В автономном режиме биометрическое распознавание может быть отключено (fail-safe) |
| ФИЗ-4 | Запрещена возможность удалённо заблокировать доступ всех жителей без физического присутствия уполномоченного лица |
| ФИЗ-5 | Tamper-detection: устройства оповещают платформу при попытке физического вскрытия |

### 2.5. Аудит и журналирование

| № | Требование |
|---|---|
| АУД-1 | Каждое событие доступа записывается с полями: `timestamp`, `device_id`, `complex_id`, `user_id`, `method`, `result` |
| АУД-2 | Журналы событий хранятся **не менее 1 года** в системах PropDevelopment |
| АУД-3 | Immutable logs — журналы доступны только для записи и чтения, без изменения |
| АУД-4 | События интегрируются с SIEM PropDevelopment в режиме реального времени |
| АУД-5 | Собственник видит журнал событий **только своей** квартиры/машиноместа через мобильное приложение |

### 2.6. Управление уязвимостями и инцидентами

| № | Требование |
|---|---|
| УЯЗ-1 | Партнёр уведомляет PropDevelopment об инцидентах, затрагивающих данные клиентов, в течение **24 часов** |
| УЯЗ-2 | Критические уязвимости в платформе партнёра устраняются в течение **72 часов** |
| УЯЗ-3 | PropDevelopment вправе приостановить интеграцию при наступлении инцидента до его устранения |

## 3. Протоколы аутентификации и авторизации

### 3.1. Мобильное приложение ↔ smart-home-gateway

| Параметр | Значение |
|---|---|
| Транспорт | HTTPS, TLS 1.3 |
| Аутентификация пользователя | OAuth 2.0, Authorization Code Flow + PKCE |
| Access token | JWT (RS256), TTL = 15 минут |
| Refresh token | TTL = 30 дней, в защищённом хранилище устройства |
| Авторизация | RBAC: собственник управляет доступом только в своей квартире/машиноместе |

### 3.2. smart-home-gateway ↔ Платформа партнёра (service-to-service)

| Параметр | Значение |
|---|---|
| Транспорт | HTTPS, TLS 1.3 |
| Взаимная аутентификация | **mTLS** — обе стороны предъявляют клиентские сертификаты X.509 |
| Дополнительный слой | API Key в заголовке `X-Api-Key`, ротация раз в 90 дней |
| Сетевая изоляция | IP allowlisting: партнёр принимает запросы только с зафиксированных IP PropDevelopment |
| Авторизация операций | JWT подписанный PropDevelopment (RS256), содержит `complex_id`, `operation`, `exp` |

### 3.3. Платформа партнёра → smart-home-gateway (Webhooks)

| Параметр | Значение |
|---|---|
| Метод | HTTPS POST на endpoint smart-home-gateway |
| Аутентификация | HMAC-SHA256 подпись тела запроса |
| Заголовок подписи | `X-Signature: sha256=<hmac>` |
| Защита от replay | Заголовок `X-Timestamp` (Unix epoch), запросы старше 5 минут отклоняются |
| Сетевая изоляция | Принимаются только запросы с IP платформы партнёра |

### 3.4. Матрица авторизации операций

| Операция | Собственник | Менеджер ЖК | ИБ-администратор | Система (партнёр) |
|---|---|---|---|---|
| Добавить номер авто в whitelist | ✅ (только свой) | ✅ | ✅ | ❌ |
| Удалить номер авто | ✅ (только свой) | ✅ | ✅ | ❌ |
| Зарегистрировать биометрию | ✅ (только свой) | ❌ | ❌ | ❌ |
| Отозвать биометрию | ✅ (только свой) | ❌ | ✅ | ❌ |
| Просмотр журнала событий | ✅ (только своё) | ✅ (весь ЖК) | ✅ | ❌ |
| Ручное открытие двери/шлагбаума | ✅ | ✅ | ✅ | ✅ (авто) |
| Просмотр статуса устройств | ✅ | ✅ | ✅ | ✅ |

## 4. Взаимодействие между системами

### 4.1. Архитектурный паттерн

```
Мобильное приложение (Витрина ЖКУ)
         │  OAuth 2.0 / JWT / HTTPS
         ▼
  smart-home-gateway ◄──► smart-home-db
  (Adapter + Circuit Breaker + Rate Limiter)
         │  mTLS + API Key / HTTPS
         ▼
  Платформа умного дома партнёра
    ├── Сервис домофонов ──► Домофон (IoT)
    └── Сервис шлагбаумов ─► Шлагбаум (IoT)
```

**Ключевые решения:**
- smart-home-gateway — единственная точка контакта с партнёром
- tenant-core-app делегирует операции умного дома в smart-home-gateway
- Биометрические данные никогда не пересекают границу PropDevelopment

### 4.2. Синхронное взаимодействие (REST API)

| Операция | Метод | Endpoint |
|---|---|---|
| Добавить разрешение (авто) | PUT | `/v1/complexes/{complex_id}/vehicles/{plate_hash}` |
| Удалить разрешение (авто) | DELETE | `/v1/complexes/{complex_id}/vehicles/{plate_hash}` |
| Статус устройства | GET | `/v1/complexes/{complex_id}/devices/{device_id}/status` |
| Ручное открытие | POST | `/v1/complexes/{complex_id}/devices/{device_id}/open` |
| Разрешить биометрию | PUT | `/v1/complexes/{complex_id}/biometric-access/{user_id}` |
| Удалить биометрию | DELETE | `/v1/complexes/{complex_id}/biometric-access/{user_id}` |

### 4.3. Асинхронное взаимодействие (Webhooks от партнёра)

**Endpoint PropDevelopment:** `https://smarthome-api.propdevelopment.ru/v1/events`

Формат события:
```json
{
  "event_id": "uuid",
  "timestamp": "2026-05-09T10:30:00Z",
  "complex_id": "complex-uuid",
  "device_id": "device-uuid",
  "device_type": "intercom|barrier",
  "user_id": "user-uuid",
  "method": "biometric|plate|call|manual",
  "result": "granted|denied|error",
  "error_code": "optional"
}
```

SLA на доставку: < 5 секунд. Retry: 3 попытки с backoff 1с → 5с → 30с.

### 4.4. Данные, передаваемые между системами

| Направление | Данные | Примечание |
|---|---|---|
| PropDevelopment → Партнёр | `user_id` (UUID), `complex_id`, статус разрешения | Без ФИО и других ПД в явном виде |
| PropDevelopment → Партнёр | `plate_hash` (SHA-256 от номера) | Реальный номер хранится только в smart-home-db |
| Партнёр → PropDevelopment | События доступа (см. 4.3) | Без биометрических шаблонов |
| **ЗАПРЕЩЕНО** | Биометрические шаблоны (в любом направлении) | Хранятся только у партнёра |
| **ЗАПРЕЩЕНО** | Видеозаписи с устройств | Не передаются в PropDevelopment |

### 4.5. Управление отказами (Circuit Breaker)

| Состояние | Условие | Поведение |
|---|---|---|
| CLOSED (норма) | < 5 ошибок за 60 сек | Запросы проходят к партнёру |
| OPEN (отказ) | ≥ 5 ошибок за 60 сек | Запросы к партнёру блокируются, устройства работают по кэшу |
| HALF-OPEN | Через 30 сек после OPEN | Пробный запрос; если успешен — CLOSED |

При переходе в OPEN: алерт в SIEM, уведомление дежурному.

### 4.6. SLA интеграции

| Метрика | Требование |
|---|---|
| Доступность API партнёра | ≥ 99.5% в месяц |
| Время ответа API | P95 < 500 мс |
| RTO при сбое интеграции | < 4 часов |
| Автономная работа устройств | ≥ 72 часов без связи с платформой |
| Уведомление об инциденте | < 24 часов |

## 6. Договорные требования к партнёру

1. **DPA** — соглашение об обработке персональных данных по 152-ФЗ
2. Обязательство хранить данные только на серверах **физически в РФ**
3. Ежегодный пентест с предоставлением отчёта PropDevelopment
4. SLA по доступности, инцидентам, патчингу уязвимостей (закреплён в договоре)
5. Запрет передачи данных клиентов третьим лицам
6. Удаление всех данных в течение **30 дней** после расторжения договора
7. Уведомление PropDevelopment об изменениях в архитектуре хранения данных
8. Право PropDevelopment на аудит системы партнёра (ежегодно или при инциденте)
